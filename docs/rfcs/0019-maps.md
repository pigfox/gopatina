# RFC 0019: Maps

- **Status:** Accepted (2026-11-28), with the recommended option on each
  of the five decisions below. The coordinator decided for the project
  lead, under his standing order of 2026-11-27: "Stop telling me what to
  do. Just get it done, okay?" The decisions: a HashMap with a fixed,
  deterministic hasher (the standard library only); copying a map moves
  it; range order is the map's own; float keys are refused; changing a
  map while ranging over it is refused. Step 1 is in place: local maps of
  strings, integers and bools to numbers, bools and strings, with no range
  yet, so no output can depend on hash order
- **Author(s):** GoPatina contributors
- **Created:** 2026-11-28
- **Discussion:** the pull request that adds this file
- **Supersedes / superseded by:** none

## Summary

Patina mode accepts maps: map types, `make`, literals, reads with the zero
value for a missing key, `v, ok := m[k]`, assignment, `delete`, `len`, `range`
and `fmt`'s printing, sorted by key. A map is a Rust `HashMap` with a fixed,
deterministic hasher. Under RFC 0017's rule it has one owner: `m2 := m`
moves it, and a function that changes a map it is passed borrows it as
`&mut`. A map that may be nil is an `Option` (Go reads a nil map as empty and
panics on a write to it). The five decisions below were made with the
recommended option on each (see Status).

## Motivation

The parity corpus (137 programs) refuses a map type in 9 programs and
`make(map[...]...)` in 3: 10 programs in all, after closures the largest
cluster that is not concurrency. None needs only maps (each also needs
something else, such as closures, `sync` or `sort`), so maps are what
unblocks those programs next. Real Go programs use maps everywhere: counting,
grouping, caches, sets (`map[T]bool`).

## Guide-level explanation

```go
counts := map[string]int{}
for _, w := range strings.Fields(text) {
	counts[w]++
}
fmt.Println(counts) // map[a:2 b:1], sorted by key, as Go prints it
if n, ok := counts["c"]; !ok {
	fmt.Println("no c", n) // n is 0, the zero value
}
delete(counts, "a")
```

In Rust:

```rust
let mut counts: HashMap<String, i64, rt::Hasher> = HashMap::default();
for w in rt::fields(&text) {
    *counts.entry(w.to_string()).or_default() += 1;
}
println!("{}", rt::show_map(&counts)); // keys sorted, as fmt does
match counts.get("c") { ... }
counts.remove("a");
```

**One owner.** `m2 := m` moves the map; using `m` afterwards is
RFC 0017's use-after-move error, in Go's terms. A function that only reads a
map takes `&HashMap`, one that changes it `&mut HashMap`: what Go's reference
semantics mean for the caller, without sharing.

**Range.** `for k, v := range m` iterates in the hasher's order, which is
fixed for a given set of keys and inserts. Go randomizes the order on every
range, so no Go program can depend on it; a program whose output depends on
it is nondeterministic in Go too (the parity corpus already skips those). A
range that changes the map it ranges over (Go allows delete during range) is
refused in this RFC.

## Reference-level explanation

| Go | Rust |
| --- | --- |
| `map[K]V`, never nil | `HashMap<K, V, rt::Hasher>` |
| a map that may be nil | `Option<HashMap<K, V, rt::Hasher>>` |
| `make(map[K]V)`, `make(map[K]V, n)` | `HashMap::default()`, `HashMap::with_capacity_and_hasher(n, ...)` |
| `map[K]V{k: v, ...}` | built by inserts, in source order |
| `m[k]` (read) | `m.get(&k).cloned().unwrap_or_default()` (the zero value) |
| `v, ok := m[k]` | `match m.get(&k)` |
| `m[k] = v`, `m[k] += v`, `m[k]++` | `insert`, `entry(k).or_default()` |
| `delete(m, k)` | `m.remove(&k)` |
| `len(m)` | `m.len()` as `i64` |
| `for k, v := range m` | `for (k, v) in &m` |
| `fmt.Print(m)` | `map[k1:v1 k2:v2]`, keys sorted as fmt sorts them |
| a write to a nil map | Go's panic, "assignment to entry in nil map" |

**Keys.** Integers, strings, bools, and structs of those: `Eq + Hash` in Rust
as in Go. Float keys are refused (decision 4): Go's NaN never equals itself,
so each `m[NaN] = v` adds an entry, which Rust's `HashMap` cannot do without a
wrapper. Pointer and interface keys are refused too, for now.

**Values.** Any type the subset holds, with RFC 0017's ownership: a value
read out is cloned when the map keeps it (`m[k]` of a slice is a copy in Go
too, of the header, sharing the elements; under one owner a slice value read
from a map is refused when the program would change it through the copy).

**Nil.** RFC 0017 step 2's non-nil analysis applies: a map variable is plain
when it is always made before use, `Option` otherwise. Reading a nil map
gives the zero value and length 0; writing panics with Go's message.

## Testing: never against Go's range order

Go randomizes the order of every range over a map, so no test may compare
it with patina mode's. The differential tests, the difftest's generated
programs and the parity corpus compare output, so each must be independent
of range order:

- The golden programs and the difftest's generator (internal/progen) only
  range over a map to compute something independent of the order (a sum,
  a count, a max), or over its keys sorted first (`slices.Sorted(maps.Keys(m))`
  once that is supported, or a sorted copy). `fmt.Print(m)` is safe: fmt
  sorts the keys.
- A test that would print in range order is a bug in the test: the
  generator never writes one, and a golden program that does is refused in
  review.
- The parity harness runs each program with Go three times and skips one
  whose output differs. testdata/parity/skip.txt lists the programs that
  differed within 20 Go runs, two of them for map iteration order
  (gobyexample/json and gobyexample/range-over-built-in-types). Another
  program found to print in range order is added there with that reason.

## Compatibility

Plain Go mode does not change. Patina-mode programs refused for "a map type"
may now be accepted; one that shares a map between two variables gets
RFC 0017's errors.

## Drawbacks

- One owner forbids sharing one map between two variables or structs, a
  common Go pattern for caches. Such programs stay refused.
- Range order differs from any one run of Go. Go itself promises nothing,
  but a person comparing outputs by eye may be surprised.

## Rationale and alternatives

The five decisions:

1. **Representation: HashMap with a fixed hasher (recommended), BTreeMap,
   or IndexMap.** A fixed hasher keeps the standard library only and O(1),
   and makes every run the same. BTreeMap iterates in key order, which looks
   more like what fmt prints, at O(log n), and cannot hold float keys at all.
   IndexMap keeps insertion order but is a crate dependency, which emitted
   crates do not have today.
2. **Copying a map: move (recommended) or share.** Sharing needs
   `Rc<RefCell<HashMap>>` and run-time borrow checks, which RFC 0017 removed
   for pointers.
3. **Range order: the representation's (recommended) or sorted.** Sorting
   every range costs O(n log n) per loop, for an order Go never promises.
4. **Float keys: refuse (recommended) or emulate NaN.** Emulating means a
   key wrapper with Go's equality and a counter for NaN entries.
5. **Changing a map while ranging over it: refuse (recommended) or allow
   delete of the current key.** Allowing it means collecting the keys first,
   O(n) memory, and Go's other cases (inserting during range) are
   unspecified anyway.

## Prior art

- TinyGo and gccgo implement Go's hash maps with randomized iteration.
- c2rust has no maps; Rust programs translated by hand from Go use HashMap
  or BTreeMap, and usually sort keys before printing.

## Unresolved questions

- Whether `map[T]bool` used as a set should become a `HashSet<T>`.
- How maps of maps (`map[string]map[string]int`) read in Rust under one owner.

## Future possibilities

- `maps` and `slices` package functions over maps (Go 1.21): `maps.Keys`,
  `slices.Sorted(maps.Keys(m))`.
- Sharing, if a later RFC brings counted references back for chosen types.
